# 추천 시스템 — 현재 구조와 앞으로 정할 것

대상: `com.cookpilot.backend.recommendation` 패키지 전체 (#27, #28 에서 들어옴).

---

## 1. 한 줄 요약

**"과거에 만족스럽게 조리한 기록에서 재료 양을 얼마나 바꿨는지 모아, 지금 만들 레시피의 재료 양을 미리 제안한다."**
수치는 전부 규칙 엔진이 계산하고, **LLM(Gemini)은 그 수치를 한국어 한 문장으로 설명하는 일만** 한다.

---

## 2. 진입점

| | |
|---|---|
| 추천 조회 | `GET /api/v1/recipes/{recipeId}/next-cook-recommendations` |
| 피드백 기록 | `PUT /api/v1/recipes/{recipeId}/recommendation-feedback/{recommendationId}` |

추천 타입은 현재 `INGREDIENT_AMOUNT` **하나뿐**이다 (`NextCookRecommendation.type` 은 문자열이지만 다른 값이 나온 적 없음).

---

## 3. 3층 분리

```
RecommendationController
  └─ RecommendationService            조합만 담당
       ├─ RecommendationDraftLoader   @Transactional(readOnly) — DB 조회 전부
       │    └─ RecommendationRuleEngine   순수 함수 — 판정·임계값 전부
       └─ RecommendationExplanationService   트랜잭션 밖 — Gemini HTTP
```

이 경계에는 이유가 있다:

- **RuleEngine 이 순수 함수인 이유** — DB 없이 단위 테스트하려고. 입력이 엔티티가 아니라 `IngredientSnapshot` / `FlavorProfile` / `EvidenceSample` 값 타입이다. 추천 임계값 상수가 전부 이 클래스 한 곳에 모여 있다.
- **설명 생성이 트랜잭션 밖인 이유** — Gemini 응답을 최대 4초(readTimeout) 기다리는 동안 DB 커넥션을 붙잡으면 동시 요청 몇 건으로 커넥션 풀이 마른다.

---

## 4. 근거 수집 파이프라인 (`RecommendationDraftLoader`)

추천 1건이 나오기까지 통과해야 하는 관문들. 하나라도 막히면 그 자리에서 빈 목록.

```
1. 대상 레시피 존재?                           없으면 404
2. 대상 레시피의 flavor profile 존재?          없으면 빈 추천
3. 대상 레시피에 양+단위가 있는 재료 존재?      없으면 빈 추천
   ("몇 g 로 바꿔라"가 성립해야 추천 가능)
4. 내 리뷰 중 rating >= 4 인 최근 100건        없으면 빈 추천
5. 그 리뷰에 개인 버전이 붙어 있나?
   - 그 조리에서 새로 만든 버전(source_review_id) 우선
   - 없으면 그때 사용한 버전(source_personal_version_id)
   - 둘 다 없으면 그 리뷰는 버림
6. 그 버전의 재료 조정 중 "양만 바꾼 MODIFY" 만 채택
   (name·unit 이 null 이어야 함 — 이름 바꾼 건 다른 재료로 본다)
7. 근거 레시피 ↔ 대상 레시피 맛 프로파일 유사도 >= 0.60
8. 재료명 정규화(공백제거+소문자) 일치 + 단위 동일
9. ratio = 조정양 / 원본양,  0.25 <= ratio <= 2.0  &&  |ratio-1| >= 0.05
   (범위 밖은 오타/실험으로 보고 버림, 5% 미만은 체감 못 한다고 보고 버림)
```

### 맛 프로파일 유사도 (`RecommendationRuleEngine.profileSimilarity`)

```
같은 레시피면            → 1.0 (taxonomy 안 봄)
sauce_bases 교집합       → +0.45
cuisine 일치             → +0.25
dish_type 일치           → +0.15
cooking_methods 교집합   → +0.15
                    통과 기준 0.60
```

**이 숫자 조합의 실질적 의미**: cuisine + dishType + cookingMethod 를 전부 맞춰도 0.55라 탈락한다. 사실상 **`소스 베이스(0.45) + 같은 국가 요리(0.25) = 0.70`** 조합만 통과한다. 즉 *"소스 계열이 같은, 같은 국가 요리"* 만 교차 근거로 쓰겠다는 선언이다.

프로파일 데이터는 `recipe_flavor_profiles` 테이블 (V9 마이그레이션). **현재는 시드 레시피 8건에 사람이 손으로 넣은 `source='MANUAL'` 행이 전부**다. `source` CHECK 제약에 `'GEMINI'`, `'FALLBACK'` 이 이미 열려 있지만 아직 아무도 쓰지 않는다.

## 5. 판정 (`RecommendationRuleEngine.draft`)

```
같은 reviewId 중복 → 최신 것 하나만
근거 < 2건         → 버림 (1회는 우연일 수 있어서)
weightedRatio = Σ(ratio × similarity) / Σ(similarity)     ← 유사도 가중평균
|weightedRatio - 1| < 0.05 → 버림
suggestedAmount = 원본양 × weightedRatio  (소수 2자리 반올림)
changePercent   = round((weightedRatio - 1) × 100)
confidence      = min(0.95,  0.45 + 근거수×0.10 + 평균유사도×0.20)
근거는 응답에 최대 5건까지만
```

마지막으로 **confidence 내림차순 상위 3건**만 응답한다.

## 6. LLM 이 지금 하는 일 (전부)

`GeminiRecommendationExplanationClient` — **문구 생성기 그 이상이 아니다.**

- 모델: `gemini-3.5-flash` (설정 기본값), temperature 0.2, maxOutputTokens 1024
- `thinkingBudget: 0` — flash 계열은 thinking 이 기본 활성이라 꺼야 출력 예산이 본문에 온전히 쓰인다
- `responseJsonSchema` 로 `{ reasons: string[] }` 강제 + `responseMimeType: application/json`
- 프롬프트에 **"추천 수치와 근거는 서버가 이미 계산했으므로 절대 변경하지 마세요"** 를 못 박음
- 추천 N건을 한 번의 호출에 배치로 보냄 (건당 1콜이 아님)

### 실패 처리가 이 설계의 핵심

다음 중 **하나라도** 어긋나면 조용히 규칙 기반 fallback 문구로 대체된다:

1. `enabled=false` 이거나 API 키가 비어 있음
2. HTTP 호출/역직렬화/파싱 중 아무 `RuntimeException`
3. 응답 후보·파트가 비어 있음
4. reasons 원소가 빈 문자열 / 180자 초과 / 줄바꿈 포함
5. `reasons.size() != contexts.size()` (개수 불일치)

**수치는 이미 서버가 계산해 둔 값이라 LLM 이 죽어도 추천 자체는 정확하게 살아남는다.** 이게 "LLM 을 문구에만 쓴" 이유다.

응답에는 출처가 그대로 실린다: `explanationSource` = `"GEMINI"` | `"FALLBACK"`, `model`, `promptVersion` (현재 `"nextcook-reason-v1"`). 프롬프트 문구를 바꾸면 v2 로 올린다 — 기능 번호(F-xx)에 묶지 않는데, 명세 개정마다 번호가 밀리기 때문.

## 7. 피드백 루프

`recommendation_feedback` 테이블에 `ACCEPTED` / `REJECTED` / `MODIFIED` 를 기록한다.

- `(user_id, recommendation_id)` UNIQUE → 같은 추천에 두 번 보내면 처음 것을 그대로 반환 (멱등)
- `explanationSource` / `model` / `promptVersion` 을 같이 저장 → **"이 문구가 어느 프롬프트에서 나왔고 사용자가 받아들였나"** 를 나중에 역추적 가능
- 재노출 억제: 그 재료의 **최신** 피드백이 REJECTED 이고, 거절 시각 이후 새 조리 기록이 없으면 다시 안 올린다. 새 근거가 쌓이면 다시 제안한다.

### 여기 구조적 구멍이 있다

**추천 자체는 서버에 저장되지 않는다.** `recommendationId` 는 `UUID.randomUUID()` 로 응답할 때마다 새로 생성된다. 즉:

- 서버는 자기가 무슨 추천을 했는지 모른다
- 피드백에 실려 오는 `suggestedAmount` / `evidenceReviewIds` / `promptVersion` 은 **클라이언트가 되돌려주는 값을 믿는 것**이다 (검증은 재료 소유·근거 리뷰 소유 정도만)
- 같은 화면을 새로고침하면 같은 추천에 다른 `recommendationId` 가 붙는다 → 중복 피드백 방지가 안 됨

## 8. 현재 상태 요약

| 항목 | 상태 |
|---|---|
| 추천 대상 | 재료 **양** 하나뿐 |
| 판정 | 100% 규칙 기반, 임계값 하드코딩 |
| LLM | 설명 문구 생성만. 실패 시 조용한 fallback |
| 프로파일 데이터 | 시드 8건 수동 입력. 자동 생성 파이프라인 없음 |
| 추천 영속화 | 없음 |
| Cold start | 사실상 추천이 안 나옴 (아래) |

**Cold start 가 심각하다.** 추천 1건이 나오려면: 개인 버전이 붙은 rating≥4 리뷰가 **2건 이상** + 그 레시피들이 대상과 유사도 0.60 이상 + 같은 이름·같은 단위 재료 + 5~100% 사이의 양 변화. 신규 사용자는 **몇 주간 아무 추천도 못 본다.**

# 정해야 하는 것

여기부터는 결정 대기 항목이다. 각 항목마다 선택지와 현재 기울어진 방향을 적었다.

## D1. 무엇을 추천할 것인가 (범위)

| 선택지 | 얻는 것 | 잃는 것 |
|---|---|---|
| **A. 재료 양만 유지** | 지금 코드 그대로. 검증·되돌리기 쉬움 | 사용자가 체감하는 변화 폭이 작음 |
| **B. 조리 단계·시간·불세기까지** | "3분 더 볶기" 같은 실제 실패 원인에 대응 | 단계 diff는 자유 텍스트라 ratio 같은 수치 판정이 불가 → LLM 필요 |
| **C. 레시피 자체 추천 ("오늘 뭐 먹지")** | 홈 화면이 살아남 | 완전히 다른 문제. flavor profile + 협업필터 필요 |

→ **결정 필요.** B 와 C 는 같은 이름을 쓰지만 완전히 다른 시스템이다. C 를 할 거면 패키지를 나눠야 한다.

**정할 것:**
- [ ] B 를 할 것인가? 한다면 단계 조정을 어떻게 수치화/판정하는가?
- [x] C 는 이 패키지인가 별도 패키지인가? → **별도(`home` 패키지)로 구현 완료.**
  `GET /api/v1/home/recommendations`. 공유하는 것은 `profileSimilarity` 함수 하나뿐이고
  임계값·랭킹·응답 형식은 전부 분리했다. 설계와 약점은 `feat-home-recipe-recommendation.md`.
  협업필터는 사용자가 mock 1명이라 불가능해서 콘텐츠 기반으로 갔다.

## D2. LLM 을 어디까지 들일 것인가 (핵심 결정)

현재는 **L1**. 어디까지 올릴지가 이 문서의 가장 큰 질문이다.

| 레벨 | LLM 역할 | 규칙 엔진 역할 | 실패 시 |
|---|---|---|---|
| **L1 (현재)** | 설명 문구만 | 후보 선정 + 수치 계산 + 랭킹 | 템플릿 문구로 대체, 추천은 정상 |
| **L2** | 랭킹·필터 보조 (어떤 추천이 지금 맥락에 맞나) | 후보 생성 + 수치 계산 | 규칙 랭킹으로 대체 |
| **L3** | 후보 **제안** (양뿐 아니라 단계·시간도) | **가드레일** — 범위·단위·재료 존재 검증 | 추천 없음 또는 규칙 후보만 |
| **L4** | 전부 (근거 요약 → 추천 생성) | 사후 검증만 | 추천 없음 |

**추천: L1 → L3 로 가되, 규칙 엔진을 지우지 말고 가드레일로 재배치.**

이유:
- L1 은 cold start 를 못 푼다. 근거 2건이 없으면 LLM 이 할 일이 아예 없다. LLM 의 사전지식(“된장찌개에 두부 반 모는 적다”)을 쓸 수 있는 유일한 레벨이 L3 이상이다.
- L4 는 검증 불가능하다. 지금 `parseReasons` 가 하는 형식 검증(180자·줄바꿈·개수)처럼, **모든 LLM 출력에 기계 검증이 붙어야 한다**는 게 이미 이 코드베이스가 세운 원칙이다. L4 에서는 검증할 기준 자체가 없다.
- 이미 `RecommendationRuleEngine` 의 `isUsableRatio` / `passesSimilarity` / `normalizeName` 은 **그대로 가드레일로 쓸 수 있다.** LLM 이 제안한 양도 0.25~2.0 범위 밖이면 버리면 된다.

**정할 것:**
- [ ] 목표 레벨은? (L2 / L3 / L4)
- [ ] L3 라면 LLM 제안에 붙일 가드레일 목록을 확정 (아래 §LLM 계약 참고)
- [ ] LLM 이 제안한 추천과 규칙이 낸 추천을 **섞을 것인가, 아니면 규칙 우선 → 부족분만 LLM 인가?**
- [ ] `explanationSource` 처럼 `recommendationSource` 를 응답·피드백에 남길 것인가? (A/B 평가에 필수)

## D3. flavor profile 을 어떻게 채울 것인가

지금은 **시드 8건 수동**. 레시피 카탈로그가 커지면 즉시 막힌다. V9 마이그레이션이 이미 `source IN ('MANUAL','GEMINI','FALLBACK')` 과 `profile_version` 을 예약해 뒀다 — 설계자가 LLM 분류를 예상하고 있었다.

| 선택지 | |
|---|---|
| **A. 계속 수동** | 카탈로그가 수십 건 규모로 멈춘다면 유효 |
| **B. LLM 배치 분류** (추천) | 레시피 등록 시 1회 호출 → 프로파일 저장. 추천 요청 경로에는 지연 0 |
| **C. 추천 시점 실시간 분류** | 지연·비용이 요청마다 발생. 이유 없음 |

→ **B 를 권한다.** 프로파일은 레시피당 1회만 필요하고 거의 안 변한다. 추천 요청 경로에 LLM 호출을 하나 더 얹을 이유가 없다.

**정할 것:**
- [ ] taxonomy 를 고정 enum 으로 잠글 것인가? (`cuisine`, `dish_type`, `cooking_methods`, `sauce_bases` 가 지금은 자유 TEXT 다 → LLM 이 `KOREAN` 대신 `Korean` 을 내면 유사도가 조용히 0 이 된다)
- [ ] 분류 실패 시 `source='FALLBACK'` 으로 무엇을 넣는가? (프로파일 없으면 추천이 아예 안 나옴)
- [ ] 유사도 가중치(0.45/0.25/0.15/0.15)와 임계값 0.60 은 수동 8건 기준으로 잡힌 값이다. LLM 분류로 넓어지면 **재조정이 필요하다.** 무엇을 기준으로 재조정하나?

## D4. 추천을 저장할 것인가

§7 의 구멍. 지금은 서버가 자기 추천을 기억하지 못한다.

| 선택지 | |
|---|---|
| **A. 현행 유지** | 테이블 하나 안 늘어남. 피드백 데이터를 신뢰할 수 없음 |
| **B. `recommendations` 테이블 추가** (추천) | 피드백이 실제 추천을 FK 로 가리킴. 재현·평가·중복방지 전부 해결 |
| **C. 응답에 서명된 토큰** | 저장 없이 위조만 막음. 중복 방지·평가는 여전히 불가 |

→ **D2 에서 L2 이상으로 갈 거면 B 는 사실상 필수다.** LLM 추천을 평가하려면 "무엇을 추천했는지"가 서버에 있어야 한다. L1 에 머무를 거면 A 로 버텨도 된다.

**정할 것:**
- [ ] B 로 갈 것인가? 간다면 TTL 은? (추천은 새 조리 기록마다 바뀐다 → 영구 보관은 무의미)

## D5. Cold start 를 어떻게 넘길 것인가

현재 신규 사용자는 **아무 추천도 못 본다.**

| 선택지 | 위험 |
|---|---|
| **A. 임계값 완화** (근거 1건, 유사도 0.45) | 우연을 개인화로 착각. 신뢰 잃으면 회복 어려움 |
| **B. 전역 통계 폴백** ("다른 사용자들은 평균 15% 줄였어요") | 개인화가 아님. 하지만 정직하게 라벨링하면 유효 |
| **C. LLM 사전지식** ("일반적으로 이 레시피는 소금이 짜다") | 근거 없는 추천. 반드시 다른 라벨/UI 로 구분해야 |
| **D. 추천 없음을 그대로 노출** | "3번만 더 요리하면 개인 추천이 시작돼요" — 진행도 표시 |

→ **D + C 조합을 권한다.** D 는 코드 변경이 거의 없고 기대치를 정직하게 관리한다. C 를 붙이면 D2 의 L3 결정과 자연스럽게 합쳐진다. **단, `recommendationSource` 로 개인 근거 기반과 사전지식 기반을 반드시 구분해야 한다** — 안 그러면 피드백 데이터가 오염돼 D2 평가가 불가능해진다.

**정할 것:**
- [ ] 근거 부족 상태를 API 로 노출할 것인가? (지금은 빈 배열만 옴 — "근거 없음"과 "추천할 게 없음"이 구분 안 됨)

# LLM 활용 계약 (D2 를 어느 레벨로 정하든 지켜야 할 것)

현재 `GeminiRecommendationExplanationClient` 가 이미 세워둔 원칙이다. 확장할 때 그대로 승계한다.

### 1. 모든 LLM 출력에 기계 검증이 붙는다
지금은 형식 검증(JSON schema + 180자 + 줄바꿈 + 개수 일치). L3 로 가면 **의미 검증**이 추가된다:
- 제안한 재료가 그 레시피에 실제로 존재하는가 (`recipe_ingredients` 조회)
- 단위가 원본과 같은가
- ratio 가 `isUsableRatio` 범위 안인가 (0.25 ~ 2.0, |ratio-1| >= 0.05)
- 제안 개수가 `MAX_RECOMMENDATIONS`(3) 이하인가

**검증에 실패한 항목은 개별로 버린다.** 지금 코드는 하나라도 어긋나면 전체를 버리는데(`return Optional.empty()`), 후보 생성에서는 부분 채택이 맞다.

### 2. 실패는 조용히 흡수하되 출처는 남긴다
`explanationSource` 패턴 그대로. LLM 이 죽어도 사용자 경험이 죽지 않는다. **단 §7 의 Live 토큰 사례처럼 "폴백이 불가능한 기능"은 예외** — `AiLiveSessionService` 는 키가 없으면 409 를 던진다. 추천은 폴백이 가능하므로 조용히 넘어가는 게 맞다.

### 3. 프롬프트는 버저닝하고 피드백에 실어 저장한다
`PROMPT_VERSION = "nextcook-reason-v1"`. 문구를 바꾸면 v2. 기능 번호(F-xx)에 묶지 않는다. **L3 로 가면 후보 생성용 프롬프트 버전이 별도로 필요하다** (`nextcook-suggest-v1`?).

### 4. 요청 경로의 LLM 호출은 배치 1회로 제한한다
지금 추천 N건을 한 번의 호출로 처리한다. connectTimeout 2s / readTimeout 4s. **호출을 늘리려면 지연 예산부터 정해야 한다.** 조리 시작 직전 화면이라 사용자가 기다리는 중이다.

**정할 것:**
- [ ] 추천 API 전체의 지연 예산(p95)은 몇 ms 인가?
- [ ] 프로파일 분류(D3-B)처럼 **요청 경로 밖으로 뺄 수 있는 LLM 호출**을 먼저 분리했는가?

### 5. 수치는 가능한 한 서버가 계산한다
현재 프롬프트의 핵심 문장: *"추천 수치와 근거는 서버가 이미 계산했으므로 절대 변경하지 마세요."* L3 로 올려 LLM 이 수치를 제안하게 되더라도, **최종 `suggestedAmount` 는 서버가 반올림·정규화해서 다시 만든다.** LLM 문자열을 그대로 응답에 싣지 않는다.

**정할 것:**
- [ ] L3 에서 LLM 은 절대값(`120g`)을 내는가, 비율(`+20%`)을 내는가? → **비율을 권한다.** 원본 양이 바뀌어도 유효하고, `isUsableRatio` 로 바로 검증된다.
